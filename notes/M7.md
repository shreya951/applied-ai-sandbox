## Feature I picked
- The starred filter

## Plan from chat

1. Data Model Changes
Add a boolean field to each note:
is_starred: bool = False
Default behavior:
New notes are not starred unless explicitly set.
Optional (if using DB):
Add a migration to introduce is_starred column with default false.
2. Route / Backend Changes
Update note creation route:
Accept optional is_starred value (default to false if missing).
Update note update route:
Allow toggling is_starred.
Update notes fetch route:
Sort logic changes:
Primary sort: is_starred DESC
Secondary sort: existing ordering (e.g., created_at DESC or id DESC)

Example logic:

Starred notes → first
Non-starred notes → after, preserving existing order among themselves
3. UI Changes
Add star toggle control:
Icon (★ / ☆) next to each note title.
Clicking toggles starred state.
Visual hierarchy:
Starred notes appear at top of list automatically.
Optional subtle highlight (background tint or filled star).
No change to note creation flow required unless you want “star on create”.
4. Edge Cases / Things to Handle
Empty state:
If no notes exist, normal empty state still applies.
All notes starred or all unstarred:
Sorting still works normally; no special casing needed.
Toggling star status:
Ensure UI updates instantly or re-fetches sorted list.
Pagination (if exists):
Starred notes should not be split awkwardly across pages.
Conflicting sorts:
Ensure only one primary ordering rule (starred first) to avoid unstable ordering.
Data migration safety:
Existing notes must default to is_starred = False.

## Workflow retro
- This workflow felt pretty structured overall because I started by locking in a clear design for the starred feature before touching any code. The biggest difference was that the data model and the sort logic were already planned out, so implementation was mostly just translating the spec into actual plans and UI changes. Claude was useful for pushing the implementation forward quickly, especially for wiring together backend and frontend changes at the same time. It did sometimes suggest extra changes that weren’t strictly needed, which I had to clean up later, but overall it was helpful for getting a working version fast. The main issue I ran into was having to double-check that the sorting logic didn’t accidentally override existing ordering behavior. Using Copilot afterward was more helpful for polishing than development. It helped clean up small syntax issues and remove some leftover code, but it wasn’t doing anything structurally important. The parallel task with sticky notes was harder to manage because switching contexts slowed me down more than expected. It worked better when I treated one tab as “planning mode” and the other as “execution mode,” instead of trying to actively code in both at once. In the future I would probably avoid fully parallel execution unless the tasks are completely independent, since even small overlaps in state made things harder to track mentally.
